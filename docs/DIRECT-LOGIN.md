# Прямий вхід і події в календарі

Outlook (робочий та особистий) і Google Calendar можуть завантажувати події безпосередньо в календар Dayframe, без Render та без клієнтських секретів. Для Microsoft використовується офіційний MSAL Browser з authorization code + PKCE, для Google — Google Identity Services token client. Це синхронізація лише для читання основного календаря, а не відображення чужої вебсторінки.

## Одноразова активація застосунку

Офіційна реєстрація застосунку потрібна навіть для особистого інструмента. Пароль від акаунта не замінює Client ID. Зареєстрованих Client ID репозиторій не містить, реальні облікові записи автоматично не авторизуються.

У Dayframe → Налаштування → Твої підключення → «Активація прямого входу в календарі» можна зберегти публічні Client ID локально. Секрети та паролі туди не вводяться.

### Microsoft

1. Зареєструвати Dayframe в Microsoft Entra із підтримкою робочих та особистих облікових записів.
2. Додати платформу **Single-page application (SPA)**, не Web.
3. Зареєструвати точну адресу повернення, показану в Dayframe. Для опублікованого сайту: `https://anastasiia1001.github.io/dayframe/oauth-redirect.html`. Для локального запуску: `http://localhost:4317/oauth-redirect.html`.
4. Додати делегований дозвіл Graph `Calendars.Read`.
5. Зберегти Application (client) ID у Dayframe. Client secret не потрібен.

Входи для робочого й особистого Outlook незалежні (`organizations` / `consumers`). Політики організації та вимога згоди адміністратора зберігаються.

### Google

1. У Google Cloud увімкнути Calendar API та налаштувати OAuth consent screen.
2. Створити OAuth клієнт **Web application**.
3. Додати Authorized JavaScript origin `https://anastasiia1001.github.io`; для локального запуску — `http://localhost:4317`. Origin не містить `/dayframe/`.
4. У тестовому режимі додати власний акаунт до test users.
5. Зберегти Google Client ID у Dayframe. Секрет не потрібен.

Запитується лише `calendar.events.readonly`.

## Щоденна робота

Натиснути «Увійти через …» → пройти офіційний вхід → надати дозвіл → події з’являться в календарі Dayframe. Повторне читання оновлює події без накопичення копій; скасовані події відкидаються. Час показано за Києвом. Дати подій на весь день не зсуваються через часові пояси.

Оновлення відбувається вручну, при поверненні фокуса та кожні п’ять хвилин у видимій вкладці. Це не миттєвий push і не синхронізація при закритому застосунку. Зміни в зовнішні календарі не записуються.

Токени прямого входу тримаються тільки в пам’яті вкладки, не в localStorage та не на сервері. Після перезавантаження вкладки потрібно увійти знову; після спливання дозволу Google — також. Microsoft намагається поновити дозвіл без вікна під час читання, якщо сеанс ще доступний. «Відключити» прибирає локальний токен; відкликати сам дозвіл можна в налаштуваннях Microsoft/Google.

## Slack і Jira

Їхні потоки читання даних не замінюються входом у звичайну вебсторінку. Офіційні OAuth-інтеграції з клієнтськими секретами працюють через наявний сервер Dayframe (локально або на хостингу). Секрети не вбудовуються в сайт. У браузері відкривається звичайний офіційний вхід, а обмін секретом виконує сервер.

Slack читає згадки й вибрані канали. Повідомлення перетворюється на завдання лише після вибору назви й дати користувачкою.

Jira Cloud читає активні завдання, призначені поточній користувачці. Справжні дедлайни відображаються як події на весь день у календарі. Завдання без дедлайну показуються в «Робота»; «Запланувати» відкриває редаговану локальну копію. Дата не вигадується як дедлайн Jira, і локальна копія не змінює Jira. Показуються до 500 завдань на кожному з перших п’яти доступних сайтів; обмеження явно позначається.

Для Jira: застосунок у `https://developer.atlassian.com/console/myapps/`, OAuth 2.0 (3LO), callback `https://YOUR-HOST/api/auth/jira/callback`, дозволи `read:jira-work` та `offline_access`. На сервері — `ATLASSIAN_CLIENT_ID` і `ATLASSIAN_CLIENT_SECRET`. Підтримується Jira Cloud, не Jira Server/Data Center. Confluence залишається вимкненою.

Тести імітують відповіді провайдерів і перевіряють протокол, відображення, оновлення, скасування, розділення сеансів та межі доступу. Вони не підтверджують реального входу або наявності дозволів у робочій організації.
